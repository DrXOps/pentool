# Подплан: Intruder с авто-подбором лимитов (вместо «Turbo»)

**Родитель:** [PLAN.md](../PLAN.md). **Обновлён:** 2026-11-23. **Статус:** идея,
оценка есть, решение владельца нужно.

## Вопрос

«Турбо-интрудер и обычный — чем по сути отличаются?». Проверено по коду
(`pro/pentool/modules/intruder_turbo.py` против `pentool/modules/intruder.py`):

| | обычный Intruder | Turbo |
|---|---|---|
| файл | `modules/intruder.py`, 863 строки | `modules/intruder_turbo.py`, 200 строк |
| ограничение параллелизма | `asyncio.Semaphore(threads)` | фиксированный пул из `threads` воркер-корутин |
| HTTP-соединения | по умолчанию (новое на запрос) | `TCPConnector(limit=threads*2, limit_per_host=threads, ttl_dns_cache=300)` — keep-alive пул |
| генерация комбинаций | ленивый итератор | тот же ленивый итератор базового класса |
| что даёт «10x» | — | только пул соединений + отсутствие материалазации комбинаций |

Вывод: **Turbo — это не другой режим атаки, а профиль транспорта.** Логика
(позиции, payload'ы, режимы Sniper/Battering Ram/Pitchfork/Cluster Bomb,
результаты, сохранение в БД) одна и та же. Отдельный класс и отдельный пункт меню
дают пользователю ложный выбор: «обычный/быстрый», тогда как правильный выбор —
«сколько параллельных запросов и с какой задержкой выдержит цель».

Дополнительно: «10x» — обещание в UI/фичах, которое нельзя подтвердить (в коде нет
замера), а скорость упирается в сервер и сеть, а не только в пул.

## Предложение: один Intruder с адаптивным лимитом

Вместо двух движков — один, с профилем нагрузки и автоподбором:

1. **Профили**: `stealth` (1–2 потока, задержка 500–1500 мс, jitter), `balanced`
   (5–10 потоков, 100–300 мс), `aggressive` (пул соединений как у Turbo, задержка 0).
   Профиль — это набор стартовых значений, а не отдельный код.
2. **Автоподбор перед стартом**: короткая проба (5–10 запросов) измеряет медианное
   время ответа и долю 5xx/429; стартовый параллелизм выбирается так, чтобы не
   упираться в таймауты; потолок — лимит лицензии (`intruder_max_threads`).
3. **Автомодуляция по ходу** (главное): контроллер раз в N запросов смотрит на
   метрики окна — средняя латентность, доля таймаутов, доля 429/503, доля ошибок TLS:
   - латентность растёт или появились 429/503 → уменьшить параллелизм, добавить
     задержку (с jitter), при повторах — экспоненциальный backoff;
   - латентность стабильно низкая, ошибок нет → осторожно увеличивать до потолка;
   - серия таймаутов → пауза и снижение до безопасного минимума.
   Всё это видно в интерфейсе: текущий параллелизм, текущая задержка, причина
   последнего изменения («latency +40%», «429 ×3», «recovered»).
4. **Совместимость**: `Turbo` становится `aggressive`-профилем (тот же пул
   соединений), отдельный модуль и фича `turbo_mode` удаляются из UI; в матрице PRO
   вместо «Turbo Mode Intruder (10x speed)» появляется «Адаптивный Intruder:
   авто-подбор потоков и задержек, модуляция по метрикам».
5. **Метрики для отчёта**: в результаты добавляются `latency_ms`, `retries`,
   `throttled` — чтобы после атаки было видно, где сервер начал отбивать запросы.

| тесты | контроллер: рост латентности → снижение; 429 → backoff; восстановление → рост; потолок лимита не превышается |

## Оценка и риски

Оценка: **2–3 дня** (контроллер + профили + UI + тесты), из них полдня — перенос
пула соединений из Turbo в базовый класс.

Риски: (а) адаптивность может «разгонять» нагрузку на чужой сервер — потолок и
минимум задержки по умолчанию консервативные, профиль `aggressive` требует
подтверждения; (б) результаты меняются по времени (недетерминированность) — метрики
пишутся в отчёт, чтобы это было видно.
