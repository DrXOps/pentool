### N1. Шапка Scanner дублирует тулбар (новое, 2026-11-23)

При переносе старт/стопа в шапку модуля (T-027) действия Scanner были добавлены и в
`header_spec()`, а старый тулбар из `compose()` **не убран**: Export, Clear,
Passive, False+, Tab, «→ Repeater» видны дважды — шапка модуля и тулбар под ней.
Видно на скриншоте пользователя («двойная шапка там, где export»).

Лечение: удалить `Horizontal(id="toolbar")` из `compose()` и `_sync_toolbar_to_tab()`,
оставить действия только в шапке (плюс `⋯` для редких). Оценка: 0.5–1 час, PRO-коммит.
Одновременно проверить Repeater/Intruder на ту же ошибку (там тулбар остался
легально — в нём живут Threads/Delay/Turbo).

### N2. `--smart <host:port>` не создаёт запись в истории сразу (новое, 2026-11-23)

Симптом: запуск `pentool --smart telemetry.lightpanda.io:443` — в истории Proxy
пусто, позже появляется **один** POST `https://telemetry.lightpanda.io:443/v2`.

Причина (лог 22:37:00–22:37:08):
1. `--smart` включает `real=True` → `_do_real_fetch_sync()` запускает **lightpanda
   fetch** в executor'е;
2. команда содержит `--wait-ms 3000` — браузер ждёт 3 секунды после загрузки, поэтому
   запрос появляется только через ~3 с (плюс ~1 с на старт процесса);
3. цель `telemetry.lightpanda.io:443` передаётся **без схемы**, lightpanda шлёт
   POST `/v2`, а не GET на хост — отсюда «только этот запрос» и странный метод;
4. в том же прогоне: `$level=warn $msg="flush" err=OperationTimedout` (телеметрия
   lightpanda не успела), то есть сам fetch тоже шёл на грани таймаута.

Лечение (обсуждается): нормализовать цель в URL со схемой; уменьшить `--wait-ms`
(параметр, по умолчанию 500–1000); показывать в истории «pending»-строку сразу
после старта, заменяя её реальным запросом; отделить «браузерный fetch» от «просто
посмотреть хост» (флаг), чтобы `--smart` не ждал браузера.

### N3. Переключение модулей — до 2 секунд, содержимое «доезжает» сверху вниз (новое, 2026-11-23)

Замер (`run_test`, 120×40, время от `_switch_to` до первого кадра / до стабилизации):

| Модуль | первый кадр | стабилизация |
|---|---|---|
| Repeater | **1392 мс** | 2160 мс |
| Scanner | 1188 мс | 1351 мс |
| Intruder | 862 мс | 1219 мс |
| Proxy | 626 мс | 866 мс |
| Settings | 544 мс | 666 мс |
| Utils | 469 мс | 650 мс |
| Target | 333 мс | 435 мс |
| Dashboard | 334 мс | 546 мс |
| Extensions | 199 мс | 314 мс |

Причины: (а) ленивое монтирование с `keep_recent=1` — вернувшийся экран собирается
заново; (б) тяжёлый `on_mount` (загрузка данных из БД, построение таблиц, колонки,
восстановление табов) выполняется до первого кадра; (в) Textual монтирует детей
последовательно, поэтому видно «доезжание» сверху вниз.

Варианты ускорения — в [subplans/tui.md](subplans/tui.md), раздел «Отзывчивость».

### N4. Мелочи из логов (новое, 2026-11-23)

- `proxy: WS history counter not found: No nodes match '#ws-history-count'` —
  повторяется на каждом монтировании Proxy: счётчик WS-истории ищется по id,
  которого больше нет (переименован при редизайне). Либо вернуть id, либо искать

### P1 — история Proxy пустеет при переключении подвкладок (2026-11-21)

Пользователь: «при переключении вкладок туда-сюда в истории прокси пропадают
строки, пока не нажмёшь фильтр — видимо не подгружаются автоматом из БД».
С ленивыми подвкладками тело HTTP History монтируется заново при возврате:
`_refresh_tab_data` вызывает `_reload_table`, но, судя по описанию, таблица
остаётся пустой до ручного фильтра. Проверить порядок: `_reload_table` идёт в
`run_worker` и может обгонять монтирование таблицы (обращение к `#request-list`
до её появления → NoMatches → тихий `logger.debug`). Нужен ретрай/ожидание
монтирования (как `_init_tab_content` в Repeater).


### P2 — Target мигает при первом открытии дашборда (2026-11-20)

При старте на долю секунды появляется экран Target поверх дашборда, затем
исчезает. Логический фикс T-031 (ensure не делает экран видимым) уже в
`develop`, но мигание осталось: экран монтируется в `ContentSwitcher` и,
видимо, один кадр успевает отрисоваться до `display = False`. Проверить
`LaptopScreenManager.mount_module`: ставить `display=False` **до** монтирования
(или через `styles.display`), а не после; проверить на реальном `--url` прогоне.

(`pentool/`), поэтому правки в `ai/` не требуют обновления `wiki/<module>.md`.

добавлена в `wiki/index.md` вручную. Если автоматизация перерастёт в
продуктовую фичу — расширить `CODE_ROOT` или добавить отдельный корень.
