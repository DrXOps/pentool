## Профилирование ТУИ перед релизом (обязательный гейт)

**Зачем.** Отзывчивость — то, что пользователь чувствует раньше функций. Отдельные
оптимизации уже сделаны точечно (ленивое монтирование экранов, `gc.freeze`, кэш слотов
шапки, индикаторы на событиях вместо опроса), но **системного замера нет**: неизвестно,
где реально упирается интерфейс при больших проектах. До релиза это нужно знать
числами, а не ощущениями.

**Когда:** последний шаг перед мержем в `main`, после шага 6 плана
[унификации](tui-unification.md) (слияние HTTP/WS-истории меняет самый горячий путь —
мерить до него нет смысла).

### Что мерить (сценарии)

Замеры на **релизной сборке** (без `--verbose`, без dev-инструментов), три конфигурации:
CPU-only ноутбук, средний ноутбук с GPU, десктоп; плюс WSL и нативный Windows.

| Сценарий | Как воспроизвести | Что смотрим |
|---|---|---|
| Старт приложения | запуск без проекта и с проектом 200k запросов | время до интерактивности, RSS |
| Переключение модулей | все 10 вкладок, холодно и повторно | время на переключение, пиковый RSS |
| Proxy: большой проект | история 50k и 200k строк, скролл, сортировка, фильтры, поиск | p50/p95 кадра, время фильтра |
| Proxy: живой поток | максимум перехвата, что держит цель (ориентир 200–500 запросов/с) | дропы кадров, рост RSS за 30 мин |
| Proxy: подвкладки | Intercept ↔ HTTP History ↔ WS History | время переключения, состояние таблицы |
| Scanner | 5–10k находок, живой лог сканирования | отзывчивость таблицы и лога |
| Intruder | 10k результатов, 200 потоков | вставка строк, прокрутка, стоп/пауза |
| Repeater | 20 вкладок с большими запросами | переключение вкладок, отправка |
| Target | дерево 10k узлов, раскрытие/фильтры | время раскрытия, отклик на клик |
| Utils | Decoder и Comparer на текстах ~1 МБ | время операции, блокировка ввода |
| Раскладка | resize 80×24 ↔ 200×60 | время перерасчёта, мигание |
| Простой | окно открыто, трафика нет | CPU и RSS в покое («не греет ноутбук») |

### Бюджеты (ориентиры, `[оценка]` — уточнить на замерах)

- кадр: p95 ≤ 16 мс для интерактивных действий (ввод, клик, переключение), p95 ≤ 33 мс
  для прокрутки больших таблиц;
- нажатие клавиши → отображение: ≤ 50 мс;
- повторное переключение модуля: ≤ 100 мс; первое (монтирование): ≤ 700 мс;
- вставка 1000 строк в историю: ≤ 150 мс;
- RSS на проекте 200k запросов: ≤ 400 МБ; за 30 минут потока — без монотонного роста;
- CPU в простое: ≤ 2 %.

### Инструменты

- Frame timings — Textual DevTools (`textual run --dev` + консоль);
- CPU — `cProfile` и `py-spy` (топ функций по времени, включая код Textual);
- Память — `tracemalloc` + `psutil`, отдельно `gc` статистика (что живёт дольше кадра);
- SQLite — `EXPLAIN QUERY PLAN` на запросах истории/находок, время на 200k строк;
- Регрессия — расширить `tests/perf/tui_deep.py` до сценариев таблицы выше, чтобы
  замеры можно было повторить одной командой.

### Подозреваемые (проверить первыми)

- вставка строк в историю Proxy по одной на запрос (идея батчинга 100–200 мс лежит в
  [backlog.md](../backlog.md));
- обновление подписи счётчика и `refresh()` на каждую вставку;
- копия HTTP/WS-конвейера до шага 6 — после слияния померить заново;
- `set_interval(1.0)` на Dashboard и таймеры автосохранения;
- раскладка: перерасчёт при resize для каждого экрана;
- чтение/запись файлов и SQLite в обработчиках (часть уже вынесена в executor, часть нет —
  см. `docs/tui-audit/REPORT.md`, E9).
