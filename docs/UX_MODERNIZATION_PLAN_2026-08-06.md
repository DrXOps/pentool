## Новые находки в этой сессии (после ручного теста)

**"Target не пополняется" + "многие запросы пролетают мимо базы" — одна и та же причина.**

В `ProxyServer._handle_http()` (`pentool/modules/proxy.py`) при сетевой ошибке
(`_send_request()` вернул `None` — таймаут, DNS-ошибка, connection refused,
unreachable host и т.п.) прокси отвечал клиенту `502 Bad Gateway` и делал
`return None`, **не эмитируя `ProxyRequestCompleted`**. Это означало:

1. `on_proxy_request_done()` в `app.py` никогда не вызывался → строка в HTTP
   History, уже созданная на этапе захвата (`ProxyRequestCaptured` →
   `add_request_row`), никогда не получала статус/ответ — выглядело так, будто
   запрос "завис" или пропал.
2. `SendToTarget` тоже никогда не постился → `TargetScreen.add_request_from_proxy()`
   не вызывался для таких запросов — SiteMap молча пропускал **любой хост, у
   которого хоть один запрос завершился ошибкой** (крайне часто — реклама,
   аналитика, CDN, Cloudflare challenge-домены, которые обычно таймаутятся или
   блокируются DNS — именно то, что видно в вашем логе:
   `brunhild.challenges.cloudflare.com: Network is unreachable`).

Исправлено — событие теперь эмитится и в этой ветке (со `status_code=0`, чтобы
было видно, что ответа не было, но сам факт запроса не терялся).

**Осталось желательным (не сделано в этой сессии) — вторичная причина "части запросов не в БД".**
Даже с этим фиксом возможны единичные потери при **сбое самой записи в
SQLite** (`ProxyService.store_request` — уже логирует `ERROR` с ретраем один
раз, финальная потеря логируется как `"request LOST from history"`). Если
после фикса #14 у вас всё ещё будут пропадать запросы — ищите в логе строку
`request LOST from history` и присылайте её, это укажет на другую причину
(например настоящую блокировку БД под нагрузкой).

## Реализовано по вашему запросу — Crawler в Target

Добавлены две кнопки в тулбар Target:
- **🕷 Crawl Scope** — обходит SpiderAPI все hosts, помеченные in-scope (если
  scope пуст — обходит все известные хосты, по аналогии с "пустой scope =

Найденные страницы добавляются в SiteMap через `TargetAPI.add_request()` и
сохраняются в БД. Отдельного модуля/вкладки Crawler не создавалось — вы
подтвердили, что использовать существующий Spider-движок достаточно.

### Техдолг: сообщение "перезапустите приложение сами" (на английском)

Сейчас после смены версии/активации лицензии приложение никак не просит
пользователя перезапустить его само — либо этот шаг не автоматизирован,
либо сообщение не выводится вовсе. Нужно:
- после `pentool license activate/trial/deactivate` и после апгрейда версии
  вывести явное сообщение **на английском**, что нужно перезапустить Pentool
  вручную (аналогично уже существующему `"Upgrade successful. Restart Pentool
  to use the new version."` в `cli/main.py:128` — взять его как образец тона/формата).
  Судя по коду сегодня, TUI такого сообщения не показывает — это отдельная
  доработка, не сделана в этой сессии (только запрошена в память/техдолг).
- Не делать автоматический restart процесса — пользователь должен сделать
  это сам (сохранение состояния/сессии внутри TUI сейчас на это не рассчитано).

### Ответ: безопасность `docs/admin.html` в публичном репо

`docs/admin.html` — рабочая админ-панель управления лицензионными ключами
(create/revoke, список всех ключей, machine_id). Секретов в самом файле нет
(токен вводится руками, живёт в `sessionStorage`), но публикация файла в
открытом репозитории раскрывает URL Cloudflare Worker'а и структуру
admin-API — это готовая разведка для подбора `X-Admin-Token` и лишняя
поверхность атаки. Рекомендация: убрать файл из публичного репо (приватный
репо или отдача с сервера за отдельной авторизацией), сама правка не
делалась — ждёт вашего решения.

### Краулер не находит level2–4 на xss-game.appspot.com

Ожидаемое поведение обычного HTTP-краулера без JS-движка: переходы между
уровнями там рендерятся через JS, а не через статичные `<a href>` в HTML —
Spider их просто не видит в сыром ответе. Решение — headless-браузер
(Playwright/Puppeteer) для JS-heavy сайтов; это отдельная крупная фича,
не оценивалась в этой сессии.

### Глобальный индикатор долгих процессов (краулер/скан/атаки и т.д.)

Подтверждённая дыра в UX — сейчас нет единого способа увидеть "что сейчас
фонит". Предложение пользователя: глобальный спиннер в шапке с
тултипом/дропдауном активных процессов. Требует отдельного архитектурного
обсуждения (откуда брать список активных `@work`-корутин по всем модулям) —
не реализовывалось в этой сессии, зафиксировано как приоритет для следующего
заход.

  долетает до Site Map (`add_request_from_proxy`), часть — нет. Возможно

  Target. Нужно сопоставить логи `PROXY SCREEN: add_request_row` и
