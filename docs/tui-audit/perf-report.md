# Профилирование ТУИ — первые замеры (2026-11-26)

**Родитель:** [../PLAN.md](../../MYPLANS/PLAN.md) → «Профилирование ТУИ».
**Методика:** [MYPLANS/subplans/release.md](../../MYPLANS/subplans/release.md), раздел
«Профилирование ТУИ перед релизом».
**Что измерено сейчас:** горячие пути, которые экран вызывает **в цикле** — построение
Arrow-таблиц, пагинация, счётчики, diff. Это чистые функции, поэтому цифры стабильны и
воспроизводимы одной командой.

```bash
uv run python tests/perf/tui_hotpaths.py     # эти числа
uv run python tests/perf/tui_deep.py         # старт приложения, переключение модулей, таблица Proxy
```

## Что цифры уже говорят

### 1. Главное узкое место: перерисовка истории Proxy конвертирует **всю** выборку

`_rows_to_arrow` на 200 000 строк — **755 мс**, на 50 000 — 248 мс. При этом загрузка
страницы берёт 300 строк (`_HISTORY_PAGE_SIZE`), то есть **данные грузятся страницами, а
рисуются целиком**: каждое «прокрутил вверх → догрузи страницу» пересобирает Arrow-таблицу
для всего накопленного кэша. Пользователь, дошедший до 50k строк, получает ~250 мс
блокировки на каждую страницу, до 200k — 0.75 с. Это нарушает красную линию гейта
(«блокировка интерфейса > 1 с») уже на 200k.

**Фикс (эффект / риск):** догрузка страницы должна добавлять строки, а не пересобирать
таблицу: `DataTable.add_rows()` для prepend-случая (или `insert_rows` с индексом 0) +
обновление только видимого окна. Эффект: убирает O(всего кэша) из пути прокрутки, остаётся
O(страницы). Риск: средний — нужно сохранить позицию курсора и скролла (сейчас это делается
через `scroll_to`), и не потерять сортировку (при сортировке порядок задаёт БД, а не кэш).
Оценка: 1 день + пилот-тест на «прокрутил вверх — вижу старые строки, позиция не прыгнула».

### 2. Результаты Intruder: 41 мс на 10 000 строк — приемлемо, но растёт линейно

`build_results_arrow` 10k = 41.5 мс, с колонкой Extract (регексп по каждой строке) — 64.2 мс.
Это разовая операция при перерисовке (фильтр, сортировка, смена вкладки), не на каждый
результат: одиночный результат идёт через `_add_result_row` (`add_rows([row])`), что дёшево.
Вывод: трогать не нужно, но при 100k строк будет ~0.4 с — тогда батчить.

### 3. Пагинация и выбор строки — не проблема

`merge_older` (200k + 300) = 3.4 мс, `pick_row` на 200k = 0.0 мс, счётчик без изменений =
0.0 мс (кэш текста работает: `HistoryCounter` не трогает виджет, когда числа те же).

### 4. Comparer: diff 5 000 строк = 26.6 мс

Ниже бюджета кадра (33 мс). На 20 000 строк будет ~110 мс — тогда нужен инкрементальный
diff или вынос в воркер.

## Что осталось измерить (следующий прогон)

Сценарии, требующие поднятого приложения (`tests/perf/tui_deep.py`, расширить):

- старт с проектом 200k запросов (время до интерактивности, RSS);
- переключение 10 модулей: холодно и повторно (цель ≤ 700 мс / ≤ 100 мс);
- Proxy: живой поток 200–500 запросов/с — дропы кадров и рост RSS за 30 минут;
- переключение Intercept ↔ HTTP ↔ WS (это же — P1 из `tech_debt`);
- Scanner 5–10k находок, Intruder 10k результатов при 200 потоках, Target 10k узлов,
  Repeater 20 вкладок;
- resize 80×24 ↔ 200×60;
- простой: CPU ≤ 2 %, RSS без роста.
