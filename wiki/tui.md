# tui

**Textual-интерфейс: приложение, экраны, виджеты, диалоги, миксины и система вкладок.**

- **Связи:** [[api]], [[core]], [[deps/textual]], [[deps/textual-fastdatatable]]
- **Код:** pentool/tui/
- **Источник:** pentool/tui/; аудит TUI 2026-11-06…12 —
  `docs/tui-audit/DECISIONS.md`, `CONVENTIONS.md`,
  ; волна 5 (порт Intruder) — см. историю git;
  волна 6 (F-026, экранирование разметки) — §39
- **Обновлено:** 2026-11-16

## Назначение

Самый крупный слой (96 `.py` + 53 `.tcss`). Реализует TUI на Textual: набор
экранов модулей, общие виджеты и систему вкладок. Правило слоёв:
`tui → modules` и `tui → storage` запрещены — только через [[api]] и
[[services]].

## Публичный интерфейс

- `PentoolApp` (`app.py`) — корневое приложение; монтирует экраны, содержит
  `ContentSwitcher` и условную загрузку PRO-экранов (Scanner, Recon).
- `screen_registry.py` — `SCREEN_MAP`, реестр экранов, ленивые импорты.
- `BaseModuleScreen` (`screens/base.py`) — база для экранов с вкладками.
- **Система вкладок**: `widgets/tab_panel.py::TabbedContentPanel` (Generic по
  типу состояния), `_TabState` / `_IntruderTabState`, стабильный `tab_uid`.
- Экраны: `proxy`, `repeater`, `intruder`, `decoder`, `comparer`, `sequencer`,
  `target`, `dashboard`, `extensions`, `settings`.
- `constants.py` — только 8 `SCREEN_*`, которые импортирует второй модуль
  (F-007); id одного экрана живёт литералом рядом со своим виджетом.

## Правила: как писать TUI-код

Единственный доминирующий класс дефектов в этом слое — **«код написан, но
никогда не выполняется»**: хендлер с неверным именем, CSS-селектор мимо DOM,
сообщение, которое никто не постит, константа, которую никто не импортирует.
Ошибки нет — просто ничего не происходит. Поэтому почти каждое правило ниже
закрыто исполняемым гвардом, а не дисциплиной.

### 1. Сначала найти, потом писать

Перед новым классом — пройти по каталогу компонентов
(`docs/tui-audit/CONVENTIONS.md`, раздел 7 «задача → компонент»). Готовое:

| Задача | Берём | Файл |
|---|---|---|
| Кнопка в тулбаре | `ToolbarButton` внутри `Toolbar` | `widgets/toolbar.py` |
| Start/Pause/Resume/Stop | `StartStopWidget` | `widgets/start_stop_widget.py` |
| Текст + копирование/формат | `ContentPanel` (или `RequestEditor`/`ResponseViewer`) | `widgets/content_panel.py` |
| Панель с id и кнопками | `ContentPanel` | там же |
| Переключатель значения кликом | `OptionCycler` | `widgets/option_cycler.py` |
| Фильтр по набору полей | `FilterBarWidget` / `HistoryFilterBar` | `widgets/filter_bar_widget.py` |
| Однотипные документы во вкладках | `TabbedContentPanel` | `widgets/tab_panel.py` |
| Таблица | `ArrowBackendDataTable` + `SortableTableMixin` | `widgets/data_table.py` |
| Модальное окно | `BaseDialog` | `dialogs/base_dialog.py` |
| Разделитель с ресайзом | `ResizeHandle` | `widgets/resize_handle.py` |
| Копирование панелей | `ContentClipboardMixin` | `mixins/content_clipboard_mixin.py` |
| Фоновая запись в БД | `AutoSaveMixin` | `mixins/autosave.py` |
| AI-зависимые элементы | `AiModeSyncMixin` | `mixins/ai_sync.py` |
| Ошибка/успех | `NotificationsMixin` / `app.notify` | `mixins/notifications.py` |

Два одинаковых класса вместо одного — это уже случалось: `Cycler` и
`OptionCycler` (F-020), три фильтр-бара (F-021), 11 диалогов мимо
`BaseDialog` (F-024). Гварды: `test_filter_bar_unified.py`,
`test_dialogs_unified.py`.

### 1a. Чужой текст — не разметка

`RichLog(markup=True)` и `Static` (`markup=True` у него по умолчанию)
разбирают строку как Rich-разметку. Всё, что пришло извне — тело
HTTP-ответа, URL из трафика, host из карты сайта, имя файла с диска, stderr
внешней утилиты, ответ сервера лицензий — попадает туда как **данные**, и
разметка делает с ним ровно одно из двух:

- **падает**: `RichLog.write("[/]")` → `MarkupError` прямо в писателе. В
  `except Exception` экрана это тихая потеря целой строки лога, без следа
  для пользователя (F-026);
- **съедает**: `a[b]c` разбирается как тег `[b]` и рисуется как `ac`.
  Пользователь видит не то, что пришло. `[link=javascript:…]` вдобавок
  создаёт кликабельную ссылку — в самом TUI безвредно, но то же тело
  уходит в HTML-отчёты (`export/`), где ссылка уже работает.

Правило: **своя разметка — литералом, чужое значение — через `esc()`**:

```python
from pentool.tui.markup import esc

log.write(f"[bold]{esc(host)}[/bold] — {count} запросов")
```

Экранируется только значение, не вся строка: `escape()` поверх строки с
нашими тегами покажет их пользователю буквально. `Static.update()`,
`Label.update()`, `Tree`-подписи (`Tree.process_label` → `Text.from_markup`)
и `ContentPanel.set_title()` разбирают разметку так же — везде значения
проходят через `esc()`, литералы остаются тегами.

Границы, где экранировать не нужно: числа и служебные строки, собранные
целиком из кода (`f"{done}/{total} ({pct})"`), и `notify()` —
`PentoolApp.notify` и `NotificationsMixin.notify` объявляют `markup=False`
(в отличие от Textual), потому что в уведомление почти всегда попадает
текст исключения или URL; кому нужен стиль — передаёт `markup=True` и
экранирует сам.

Обратная ошибка тоже встречается: `RichLog` без `markup=True` (такой был у
`#feed-log` дашборда) показывает пользователю `[dim cyan]…[/dim cyan]`
служебным текстом — весь фид писался тегами, а парсер их не включал.

Гвард — `tests/unit/tui/test_markup_escaping.py` (12 тестов через живые
виджеты: пропавший кусок URL и `MarkupError` при записи строки).

### 2. Стили — только `.tcss`

```python
# ✓
_CSS = (Path(__file__).parent / "my_widget.tcss").read_text(encoding="utf-8")

class MyWidget(Widget):
    DEFAULT_CSS = _CSS
```

Строка CSS в `.py` запрещена (F-025): её не видит ни гейт селекторов, ни
grep, ни подсветка. Все 10 исторических inline-CSS переведены 2026-11-12.

Дальше:

- **Цвета — только `$token`.** Hex, `rgb()`, `hsl()`, `ansi_*` запрещены:
  тема не перекрасит виджет. `!important` запрещён — он прячет конфликт
  специфичности. Сейчас ровно 0 и того, и другого (F-030).
- **`BaseDialog` уже центрирует подклассы** (`align: center middle` в его
  `DEFAULT_CSS` матчит подклассы по типу — проверено запуском `pilot`).
  Повторять `MyDialog { align: center middle }` не нужно: это шум, который
  прячет настоящую геометрию (F-024/F-038).
- **Общий селектор — один владелец.** `.toolbar-sep` объявлен в
  `widgets/toolbar_button.tcss`; повторять его в диалоге нельзя.
  Исключения — только через явный список в гварде.
- **Общий вид — общий класс, а не копия правила.** Панельный заголовок
  (`height: 1` + `background: $primary-darken-3` + `padding: 0 1`) лежал копией
  в семи файлах; теперь это `.panel-title` в `app.tcss`, а правила виджетов
  держат только отличия (`color`, `text-style`, `layout`, ширина), класс
  вешается в Python (F-038, 2026-11-16). Копию видно только по совпадению трёх
  свойств — глазами её никто не ловит, поэтому перед новым заголовком сначала
  ищи существующий класс. Виджету без места сборки (как `ActivityIndicator`)
  класс добавляется в `__init__` через `add_class()`, чтобы новые точки
  монтирования его не забыли.
- **Отступ от краёв экрана — один на всё приложение.** `Screen { padding: 0 2 }`
  в `app.tcss` (диалоги — `ModalScreen`, без поля; на узком терминале 0 1).
  До 2026-11-17 поле задавалось внутри отдельных экранов: у дашборда карточки
  стояли с полями, а proxy/intruder/target прилипали к краям, и «рамка»
  приложения выглядела по-разному в каждом модуле. Проверка числом, а не
  глазами: левый край содержимого любого экрана обязан быть `x=2`
  при ширине 120.
- **Разделители в тулбарах расставляет помощник, а не человек.**
  `Toolbar.grouped(btn_a, btn_b, …)` вставляет `.toolbar-sep` между каждой
  парой сам (`Toolbar.buttons(…)` — то же для `yield from`). Раньше `Toolbar.sep()`
  писали руками, и при добавлении кнопки черту забывали — отсюда повторяющееся
  «Add и Clear слиплись», «Drop и Forward без черты». Если группа кнопок
  действительно должна стоять без черты (фильтр-бар, встроенные кнопки
  `ContentPanel`), это осознанное исключение, а не забывчивость.
- **Селектор обязан совпадать с DOM.** Гейт: `uv run python tools/check_tui_css.py`
  (CI + pre-commit). Он сверяет каждый класс/id/тип из `.tcss` с литералами в
  `pentool/tui`, включая Textual-овские типы и классы из `DEFAULT_CSS`.
- **Атрибутных селекторов в Textual 8 нет.** `[id^="…"]` — `TokenError` при
  разборе, а не «селектор мимо». Per-tab виджеты несут и id
  (`f"{suffix}-{tab_id}"`), и **класс** с той же базой; `.tcss` селектит по
  классу (F-008).
- **Не собирать `DEFAULT_CSS` из другого через `.replace()`** по имени класса:
  переименование молча ломает вторую полусотню правил (F-021). Общий стиль —
  один файл, селекторы по общему базовому классу.
- **Каждый `.tcss` должен кем-то загружаться.** Файл, который никто не
  читает, — хуже отсутствующего: он выглядит как стиль (F-038;
  `menu.tcss`, `menu_bar.tcss` — единственные два исключения, оба мёртвые).
- **Правило, корень которого — предок виджета, живёт в `app.tcss`.**
  Textual префиксует первый селектор `DEFAULT_CSS` типом самого виджета
  (`textual/css/parse.py:174`: `if scope and selectors[0].name != scope`).
  Поэтому `Screen.narrow InspectorPanel { … }`, написанное в
  `screens/proxy/screen.tcss`, разбирается как
  `ProxyScreen Screen.narrow InspectorPanel { … }` — и не совпадает никогда,
  без единой ошибки в логе. Такие правила (адаптив по ширине, глобальные
  состояния) кладём в `pentool/tui/app.tcss`, где скопа нет. Гейт этого не
  ловит: селектор валиден, он просто не матчится.

Гвард: `tests/unit/tui/test_css_hygiene.py` (четыре правила выше, проверено
мутациями: строка CSS в `.py`, hex-цвет, повторное центрирование, второй
владелец общего селектора — каждая роняет тест).

### 3. id и адресация

- **kebab-case**, префиксы: `btn-*` (кнопки), `panel-*`/`cp-*` (панели),
  `tab-*`, `screen-*`.
- **Контейнеры не задают id по умолчанию.** Все экраны смонтированы
  одновременно внутри `ContentSwitcher`; общий `id="toolbar"` делает
  `query_one("#toolbar")` недетерминированным (F-006, F-018).
- **Один id — один узел на пути исполнения.** Два узла с одним id делают
  `query_one` неоднозначным: без типа он вернёт первый, с типом — поднимет
  `WrongType`, и в `except Exception` это тихая потеря функциональности.
  Именно так `ComparerScreen` не рендерил диф: `Vertical` и её `ContentPanel`
  оба звались `cmp-diff-area`, а `query_one("#cmp-diff-area", ContentPanel)`
  падал `WrongType`. Гейт `tools/check_tui_css.py` падает на повторе `id=`
  литерала в одной функции; `if`/`else` и `try`/`except` различаются, поэтому
  `ContentPanel.compose` (TextArea в одной ветке, RichLog в другой) легален.
- **Per-tab id строятся из константы, а не из литерала с двух сторон.**
  `_TabId` в `screens/intruder/screen.py`: 38 суффиксов, монтаж и
  `query_one` читают одну таблицу. Опечатка в литерале не ловилась ничем —
  таб монтируется, а `query_one` падает `NoMatches` только когда пользователь
  откроет именно эту вкладку (F-023/F-030). Гвард —
  `tests/unit/tui/test_intruder_tab_ids.py`.
- **Виджет ищется по `content_widget`, а не по выдуманному id.** `TextArea`
  внутри `ContentPanel` называется `#cp-body-widget`; поиск `#editor-area`
  молча падал в `except Exception` — маркер «*» не появлялся никогда
  (F-031, 2026-11-12).
- **Константы `constants.py`** — только те, что читает второй модуль; иначе они
  декорация (`test_constants_are_used.py`).
- **Состоянию, пришедшему извне, присваивается новый `tab_id`.**
  `TabbedContentPanel.action_new_tab(state=...)` берёт состояние из БД, где
  `tab_id` пустой или от прошлого запуска, и обязан переписать его на только что
  сгенерированный: per-tab id строит владелец (`_wid(tab_id, …)`), и со старым
  `tab_id` тело монтируется под одним id, а все `query_one` ищут другой —
  вкладка навсегда остаётся пустым placeholder'ом, без единой ошибки в логе.
  `tab_uid` (ключ персистентности) при этом не трогается (2026-11-12).
- **Ключи, которые читает восстановление, сверяются с теми, что пишет
  хранилище.** `dict.get("name", …)` на словаре с ключом `tab_name` не падает —
  срабатывает дефолт, и все восстановленные вкладки получают одинаковое имя.
  Гвард `test_intruder_tab_restore.py::test_every_key_read_here_is_produced_there`
  сравнивает AST-сбор `td.get(...)` в `_do_load_tabs_from_db` с ключами
  return-словаря `IntruderStorage.get_tabs`. Общее правило: у `.get()` на
  внешних данных всегда есть тихий дефолт, поэтому имя ключа — контракт,
  и его надо проверять, а не помнить.

### 4. Сообщения и хендлеры

- **`@on(...)` в обычном миксине не регистрируется** — Textual собирает
  декораторы только из `__dict__` конкретного класса. В миксинах — только
  именованные хендлеры, они резолвятся по MRO (F-001, ADR-3).
- **Имя хендлера выводится из `Message.handler_name`** = `on_` + snake_case
  от `__qualname__`. `ProxyDataTable.ScrolledToTop` →
  `on_proxy_data_table_scrolled_to_top` (одно подчёркивание); двойное — только
  у классов с ведущим `_`. Ошибка в имени = молча мёртвый хендлер (F-041).
  Гвард — `tests/unit/tui/test_handler_name_dispatch.py`.
- **Не выдумывать сообщения**: `DataTable.RowActivated` в Textual 8 нет,
  `Static.Clicked` нет (мышь на `Static` — `on_click(event: events.Click)`,
  двойной клик — `event.chain == 2`).
- **Виджет → родителю через `Message`, не через обход `self.parent`.** Обход
  «первого предка с таким методом» попадает в чужой экран (ADR-10).
- Вложенный `Message` в виджете — это норма, а не исключение: таблица ничего
  не знает об экране, она постит `ContextMenuRequest`.
- **Хендлер без виджета — мёртвый код, и он молчит.** `@on(Msg, "#some-id")`
  срабатывает только при существующем виджете с этим id; если кнопку убрали,
  а обработчик оставили, ни импорт, ни запуск, ни тесты этого не заметят.
  Так прожили пять недель «Clear results» и «Export CSV» (потеряны в
  `cb11bfd`) и кнопка Save на вкладке Settings→AI (потеряна в `0f563b3`:
  MCP-порт и путь к модели читались из конфига, но сохранить их было нечем).
  Гвард — `tests/unit/tui/test_on_selectors_resolve.py`: AST-сбор всех
  `@on(..., "#id")` против всех созданных id (`id=`, второй позиционный
  аргумент `ToolbarButton`, префикс f-строки вроде `cp-btn-{key}`).

### 5. Воркеры и асинхронность

- `run_worker(..., group=..., exit_on_error=False)` — и отмена по **группе**.
  `WorkerManager` умеет ровно шесть операций: `add_worker`, `cancel_all`,
  `cancel_group`, `cancel_node`, `start_all`, `wait_for_complete`. Вызов
  несуществующего `cancel(name)` даёт `AttributeError`, который
  `except Exception` превращает в тихий no-op (F-045).
- **Голый `asyncio.create_task` для задач внутри App запрещён** — задача не
  отменяется при закрытии экрана и пишет в закрытую БД (F-014). Прецедент:
  техдетект живёт в `auto_scope._spawn_tech_detect`, группа `tech-detect`.
- В теле хендлера — только постановка воркера; БД, сеть и файлы — внутри.
- **`mount()` асинхронен: сначала `await`, потом читать DOM.** `mount`
  планируется в очереди сообщений, а не вставляет детей сразу, поэтому
  `pane.mount(inner)`, за которым без `await` идёт `query_one`, попадает в
  «виджета ещё нет» — а `except Exception` вокруг превращает это в тихий
  no-op. Пока хелпер монтирования и загрузки данных планировались **двумя
  `call_after_refresh` в одном батче**, восстановленный из БД таб Intruder
  показывал пустой список payload'ов: `_refresh_payload_list` искал `ListView`
  раньше времени и глотал `NoMatches`. Правило: монтирование делает `async`-
  метод с `await pane.mount(...)`, и данные грузятся его последней строкой —
  один путь, один порядок. Вторая половина правила:
  `TabbedContentPanel` постит `TabCreated` **до** того, как тело таба
  собрано, поэтому пачечное восстановление из БД (вкладки создаются подряд,
  активна последняя) наполняет данными только активную; данные остальных
  приходят на `TabActivated`. Гвард —
  `tests/unit/tui/test_intruder_toolbar_wiring.py::TestRestoredTabShowsItsData`
  (пачка из двух вкладок: последняя покрашена сразу, первая — при открытии).
- **Значения per-tab виджетов берутся из состояния, а не из литерала.**
  Подпись и описание типа атаки собирались строкой «Sniper ▼», и таб,
  поднятый из БД с `battering_ram`, врал о собственном режиме. Тот же тест.
- **«Было» читается до того, как состояние обнулили.** В
  `on_intruder_filter_bar_changed` строка `had_extract = bool(...)` стояла
  после трёх присваиваний, которые очищают `tab.grep_extract_patterns`, —
  то есть всегда вычислялась уже по пустому списку. Паттерн добавлял колонку
  «Extract», а снятие фильтра её не убирало: колонка оставалась в таблице
  пустой. Гвард `test_intruder_extract_column.py` проверяет оба направления,
  а не только добавление. Общее правило: при сравнении с предыдущим
  состоянием `previous = ...` идёт первой строкой обработчика.

### 5a. Состояние, разделённое между табом и глобальным toolbar

Порт Intruder на мультитаб оставил один набор Threads/Delay/Turbo и одну
таблицу подсказок — как в однотабной версии. Оба допущения сломались молча,
и оба лечатся одним правилом: **у каждого виджета ровно один владелец, и
переезд значения между владельцами — явный вызов, а не побочный эффект.**

- **Виджет в глобальном контейнере описывает активный таб — значит, таб
  обязан принять значение, когда перестаёт быть активным.**
  `_sync_toolbar_from_tab` пушил Threads/Delay/Turbo из таба в toolbar на
  активации, но обратного пути не было: ввести 77 потоков, уйти на другой
  таб и вернуться — поле снова 10, а `action_start_attack` читает именно
  поле, так что «видимое» значение и было рабочим. Читать надо в
  `TabDeactivated` (`_save_toolbar_to_tab`), причём **до** того, как toolbar
  перерисуется под новый таб. Пустое поле — не ноль, а «дефолт»: оставляем
  последнее настоящее значение.
- **Читать обратно можно только у того таба, чьи значения toolbar и
  показывает.** Соблазн «сохранить на `TabDeactivated`» сам по себе
  недостаточен: при пачечном восстановлении вкладки создаются подряд, и
  `_sync_toolbar_from_tab` успевает пройти лишь для последней, поэтому
  `TabDeactivated` предыдущих приходит, когда в toolbar лежат **чужие**
  числа — запись в них превращала восстановленные из БД 55 потоков в
  дефолтные 10. Поэтому экран помнит `_toolbar_tab_id` (кто сейчас
  отражён) и пишет в таб, только если они совпали. Это общее правило для
  любого «зеркала» одного состояния в общем контейнере: у зеркала должен
  быть явный хозяин.
- **Создание вкладки не постит `TabDeactivated`.** `TabbedContentPanel.
  action_new_tab` делает `tc.active = tab_id` до того, как тело таба в DOM,
  поэтому обработчик Textual (`on_tabbed_content_tab_activated`) молчит, и
  владелец не узнаёт, что прежний таб перестал быть активным. Панель постит
  `TabDeactivated` сама, до смены `_active_tab_id`. Проверено: по одному
  сообщению на путь, дублей нет.
- **Декорации виджета ставятся после его монтирования, а не в `on_mount`.**
  `compose` Intruder создаёт пустые `TabPane`; тела собирает
  `_mount_tab_body`. Подсказки ставились из `on_mount` по
  `#btn-add-marker-<tab_id>` — таких id ещё не существовало, `NoMatches`
  глотался `except Exception`, и подсказок не было ни у первого таба, ни у
  новых. Start/Stop при этом вообще не имеют суффикса таба: они в
  глобальном `compose`, и `_wid(tab_id, "btn-start")` — заведомо промах.
  Две таблицы, два места применения: `_GLOBAL_TOOLTIPS` в `on_mount`,
  `_TAB_TOOLTIPS` — в конце `_mount_tab_body`.
- **Пару «подпись + описание» правит один писатель.** Тип атаки показывают
  два виджета (кнопка и `Static`), и каждый писатель — меню, загрузка из БД,
  авторазметка — правил их по-своему: `_do_load_state` писал в кнопку
  `⚡ Sniper` и не трогал описание, а активация вкладки не трогала ни то, ни
  другое, поэтому вкладка с `battering_ram` показывала сниперскую подпись.
  Теперь единственный писатель — `_sync_attack_type_ui(tab)`, и его зовут
  все три пути, включая `_load_active_tab_content` (активация вкладки).
- **Callback всплывающего меню адресует таб, из которого меню открыли, а не
  активный.** Пока `_on_select` брал `_active_tab`, а рисовал по
  `t_id`, смена вкладки при открытом меню меняла один таб и перерисовывала
  другой. Поэтому `_template_editor`, `_update_payload_select`,
  `_refresh_payload_list`, `_highlight_nth_marker` и `_auto_save_state`
  принимают `tab` параметром — иначе в БД уходил соседний таб.

Гвард — `tests/unit/tui/test_intruder_tab_state_survives.py`: значения
вводятся в настоящий `Input`, вкладки переключаются настоящим
`switch_to`, подсказки и подписи читаются с живых виджетов.

### 6. Подписки и таймеры

- `EventBus.subscribe` / `Config.add_observer` — всегда парная отписка:
  на уровне виджета в `on_unmount`, для App в `_on_exit_app`. Хендлер
  хранится в атрибуте, иначе `unsubscribe` нечего передать.
- `_on_exit_app` — единственный выход: `action_quit` не покрывает
  `app.exit()` из кода, сигнал и падение (ADR-12).
- **Таймеры снимать вручную не нужно**: `set_interval`/`set_timer` живут в
  `MessagePump._timers` (`WeakSet`), Textual останавливает их при unmount
  (`message_pump.py:533`, `Timer._stop_all`). Это проверено чтением исходника
  8.2.8, а не предположением (F-013). Хранить `self._ticker` незачем, если
  значение нигде не читается.

### 6a. Горячие клавиши

- **Имя клавиши — это то, что присылает парсер Textual, а не то, как клавиша
  называется на клавиатуре.** `Binding("ctrl-at", …)` принимается молча,
  печатается в футере и никогда не срабатывает. Ctrl+Space приходит как
  `ctrl+@` (классический терминал, байт NUL →
  `_ansi_sequences`: `"\x00": (Keys.ControlAt,)`) либо как `ctrl+space`
  (Kitty-протокол, `CSI 32;5u`); `ctrl-at` не производит ни один протокол.
  Поэтому «Ctrl+Space = Send» в Repeater годами работал только в pilot-тестах:
  `pilot.press("ctrl+at")` передаёт имя клавиши дословно (F-052).
- Ctrl+I и Ctrl+H недостижимы по той же причине: терминал шлёт байты Tab и
  Backspace, а `KEY_ALIASES` диспетчеризация не раскрывает. `F5` — потому что
  Textual отдаёт строчное `f5`.
- Гвард — `tests/unit/tui/test_hotkey_keys_are_reachable.py`: множество
  достижимых имён собирается из `XTermParser` и `ANSI_SEQUENCES_KEYS`, а не
  выписывается руками; список известных мёртвых клавиш — трещотка, которая
  может только сокращаться.
- **Одно действие на нескольких клавишах — норма**, копия «та же клавиша + то
  же действие» — нет: второй `Binding` не сработает никогда. Проверяет
  `test_app_startup.py::test_bindings` (`_KNOWN_UNREACHABLE` — единственное
  исключение из правила «мёртвых клавиш нет»).
- **Таблица хоткеев одна.** `defaults.py` — источник `BINDINGS` и содержимого
  реестра; экран настроек читает реестр (`registry.groups()` +
  `registry.get_entries`), а не держит свою копию: вторая копия успела
  разойтись с настоящей (там были `ctrl+i` и `ctrl+space` — клавиши из
  `_KNOWN_UNREACHABLE`). Группа хранится **ключом реестра**, а не полем
  `HotkeyEntry`: поле-копия у неглобальных записей молча оставалось
  `"global"`. Если когда-нибудь появится переназначение, оно обязано идти через
  реестр и переписывать `BINDINGS` смонтированных экранов; экран, который
  просто показывает «saved», — это дефект, а не заглушка (F-035). Гвард —
  `test_hotkey_settings_is_honest.py` (состав таблицы сверяется с реестром;
  в `compose` нет `Button`/`Input`; нет вызовов `.notify(...)`), а
  `test_hotkey_keys_are_reachable.py` берёт список групп из реестра — новая
  группа не может проскочить мимо проверки клавиш.

### 8. Исключения

`except Exception: pass` в новом коде запрещён (ADR-6; исторические места
чинятся при касании, рост блокирует `tools/check_silent_except.py` — трещотка
считает молчаливые хендлеры по файлам и позволяет только снижать счётчик).
Именно они скрыли F-001…F-005, F-041…F-045 и баг с `#editor-area`.

Счётчик доведён до нуля: 297 → 284 (базовая линия на старте) → 0 за 13 волн
разбора, по файлу за раз, руками. Базовая линия пуста, поэтому **любой** новый
`except Exception: pass` роняет pre-commit и CI, а не только «лишний сверх
нормы». Что осталось за пределами первой трещотки: 585 широких
`except Exception`, которые ни логируют, ни пробрасывают — по всему
`pentool/`, на 92 файлах (это ровно `ruff BLE001`; сырой AST видит 749, но
руфф снимает хендлеры с логом или `raise`). Массовой правки не будет: вторая
трещотка `tools/check_broad_except.py` с базовой линией
`tools/broad_except_baseline.json` держит потолок на файл, `--update` только
понижает, гейт блокирующий в CI и pre-commit. Когда счётчик дойдёт до нуля,
`BLE` переезжает в `select` в `pyproject.toml`, а инструмент снимается — так
уже вышло с первой трещоткой.

Пункт 1 ADR-6 в хендлерах выполнен и стал механическим: 77 обработчиков в
`on_*`/`action_*`/`watch_*`/воркерах пишут сбой трейсбеком, а не строкой.
Узкие хендлеры называют ровно ожидаемую пару причин (`NoMatches` +
`LookupError` — «таба нет», `InvalidThemeError` — тема, `RowDoesNotExist` —
курсор таблицы, `ValueError` — разбор числа); где причина действительно любая
(`push_screen` диалога, `exec_module` внешнего файла, очистка пяти сеттеров
прокси) — `logger.exception` с комментарием, почему широкий `except` оставлен
осознанно. Гвард `tests/unit/tui/test_handler_exceptions_logged.py` знает ровно
четыре формы трейсбека (`logger.exception`, `exc_info=True`, `err(exc, ...)`,
`raise`) и валит `logger.debug("...: %s", exc)`.

Каждый разобранный хендлер описан в комментарии через **последствие**: не «что
за ошибка», а «что пользователь увидит, если её проглотить». Так волна
молчаливых исключений превратилась в поиск реальных дефектов — гейт лицензии
fail-open, Intercept, отправлявший исходный запрос вместо правленого,
`_raw_full`/`get_text()` в Repeater, панель деталей Proxy под чужой строкой,
потеря scope в Target, зависший индикатор паука, потеря шаблона вкладки в
Intruder, незахваченная мышь после контекстного меню.

- Хендлер, действие, воркер — `except Exception` только с трейсбеком:
  `logger.exception(...)`, `logger.error(..., exc_info=True)`, `err(exc, ...)`
  или `raise`. Проверяет `tests/unit/tui/test_handler_exceptions_logged.py`.
- Опциональный `query_one` — `except NoMatches`, точечно. Это тоже стало
  механическим: каждый `try`, чьё тело состоит только из `query_one`/`query`,
  ловится `NoMatches`, и это проверяет гвард
  `tests/unit/tui/test_no_matches_is_precise.py` (AST + мутация подсаженным
  кодом). Широкий `except Exception` вокруг `query_one` делал то же самое, но
  заодно глотал `AttributeError` от опечатки в имени метода — ошибку
  программиста, которую надо видеть. Где тело делает ещё что-то (`.update()` с
  вычислением), гвард требует хотя бы записи в журнал.
- Вспомогательный метод из хендлера — пусть всплывает: диспетчер покажет.
- **Сбой проверки не должен работать на пользователя.** Гейт лицензии
  (`_switch_to`) был написан как `except Exception: pass` — то есть
  нечитаемая лицензия открывала платный модуль. Правило: когда проверка
  отвечает на вопрос «можно ли», ошибка чтения — это «нет», а не «можно».
  Гвард — `tests/unit/tui/test_license_check_fails_closed.py`.
- Запись о сбое — часть поведения, а не украшение: `logger.debug` с причиной
  ставится даже там, где падение безвредно (диагностика, фокус, индикаторы).
  Читатель журнала должен отличать «нечего было делать» от «не получилось».
### 8a. Как логировать: уровень выбирается по последствию

Правило, по которому пишется любой новый `except` и по которому чинится долг:

| Что случилось | Уровень | Форма |
|---|---|---|
| потеря или порча данных пользователя (не сохранилось, не восстановилось) | `error` | `logger.error(..., exc_info=True)` или `logger.exception(...)` |
| операция не выполнена, данные целы (не прочитать, не применить, не отправить) | `warning` | тоже с трейсбеком |
| косметика UI (tooltip, label, подсветка, курсор, индикатор) | `debug` | строка допустима |
| ожидаемое отсутствие (опциональный `query_one`) | без лога | узкий `except NoMatches` |
| проверка «можно ли» (лицензия, доступ) при сбое чтения | `error` + «нет» | fail-closed |

Три механических гварда закрывают три **разных** слоя — их легко перепутать,
потому что строка во всех трёх выглядит как `except Exception`:

| Слой | Что запрещено | Гвард | База |
|---|---|---|---|
| 1 | `except Exception: pass` — тело только `pass` | `tools/check_silent_except.py` | пусто (0) |
| 2 | хендлер/воркер пишет строку вместо трейсбека | `tests/unit/tui/test_handler_exceptions_logged.py` | — |
| 3 | широкий `except` в **пути данных** молчит о причине | `tools/check_logging_policy.py` | пусто (0) |

Третья трещотка — не то же, что вторая: `tools/check_broad_except.py` считает
**все** широкие `except` (`ruff BLE001`) и держит потолок на файл, а третья
смотрит только пути данных и требует честного лога. Работа по слою 3 уменьшила
и счётчик слоя 2: ruff не считает обработчик слепым, если в нём есть лог или
`raise`. На 2026-11-17 остаток второго слоя — 430 мест (было 585), и это
косметика UI в основном, а не потери.

**Путь данных** — функция, чьё имя содержит `save`/`store`/`persist`/`commit`/
`restore`/`load`/`write`/`export`/`import`/`flush`/`switch_db` и не содержит
косметических слов (`theme`, `layout`, `tooltip`, `label`, `hint`, `highlight`,
…). Внутри неё широкий `except` обязан либо пробрасывать, либо писать
`warning`+ с трейсбеком: молчание здесь означает «сохранил», хотя не
сохранилось.

Единственный законный способ промолчать — прагма с причиной на строке `except`:

```python
except Exception:  # logging-ok: файл необязательный, шум в журнале вреднее
    return
```

Прагма без причины — это тот же молчаливый `except`, только длиннее.

Долг слоя 3 (149 мест на 29 файлах на 2026-11-17) закрыт в тот же день за девять
шагов пофайловой чистки. Сейчас база `tools/logging_policy_baseline.json` **пуста**,
то есть любой новый широкий `except` в пути данных без честного лога роняет
pre-commit и CI — как и у слоя 1. Чинилось конвейером `.claude/tmp/f009/`:
бэкап → правка → компиляция → сравнение ruff «до/после» → тесты модуля → откат
при поломке; после каждого файла `python tools/check_logging_policy.py --update`
понижал потолок. Массовая автозамена запрещена: замер 2026-11-16 показал, что
доказать сужение автоматически можно лишь для 34 мест из 585.

### 8б. Уровень для горячего пути: `DEBUG`, а не `INFO`

Правило, найденное по итогам роста журнала (T-021: **4,7 ГБ за неделю**) и аудита
унифицированности (T-026):

- `INFO` — **жизненный цикл**: старт/остановка модуля, переключение проекта,
  перезагрузка таблицы, смена БД, сохранение проекта.
- `DEBUG` — всё, что происходит **на единицу данных**: пойманный запрос, тик
  таймера, сброшенная пачка строк, обработанная строка таблицы.
- `WARNING`/`ERROR` — сбой (и по правилу §8а — с трейсбеком там, где это путь
  данных).

Почему это не придирка: `logging.FileHandler` пишет и **сбрасывает** буфер на
каждой записи, то есть строка `INFO` на каждый пакет — это I/O в критическом
пути обработки трафика, плюс журнал растёт линейно по трафику и `grep` по нему
перестаёт работать.

Замер до/после (Proxy, три строки `add_request_row` / `update_request_row` /
`_store_request` переведены в `DEBUG`): журнал больше не растёт на каждый
захваченный запрос; ротация — 50 МБ × 10 архивов (`pentool/core/logging.py`,
`PENTOOL_LOG_MAX_BYTES` / `PENTOOL_LOG_BACKUP_COUNT` для тестов).

Гвард: `tests/unit/tui/test_logging_levels.py` — AST-проверка, что в методах
`add_*`/`update_*`/`_store_*`/`_flush_*`/`_on_bus_*`/`_tick`/`push_request` нет
`logger.info` (там разрешены `debug` и `warning`+ с трейсбеком на сбоях), плюс
проверка ротации в `setup_logging`.


Почему это не «переделывается каждую сессию»: слои 1 и 2 закрыты в волнах
2026-11-15 и держатся гвардами (счётчик молчаливых = 0 и не растёт), слой 3 до
2026-11-17 не начинался — он был заморожен трещоткой осознанно, чтобы не
делать недельную правку без компаса. Гвард слоя 3 появился 2026-11-17, поэтому
дальше долг только уменьшается.

  снапшота (передавали объект вместо строки).
- Снапшоты: baseline без теста, тест без baseline и два одинаковых
  baseline — ошибка (`tests/snapshot/test_snapshot_inventory.py`).

### 10. Поля сообщений, готовность монтирования и детерминизм снапшотов

Три правки одного класса — «механизм написан, а эффекта нет»: два экрана молча
теряли работу пользователя, а снапшот-слой был зелёным ровно потому, что не
видел того, что должен ловить.

- **`TextArea.Changed` и `TextArea.SelectionChanged` несут `text_area`, а не
  `widget`.** Оба хендлера Intruder (`on_template_text_changed`,
  `on_template_selection_changed`) читали `event.widget`, то есть поднимали
  `AttributeError` на каждое нажатие и каждое выделение в шаблоне; стоящий там
  `except (LookupError, NoMatches)` эту ошибку не покрывал, и она уходила в
  диспетчер Textual. Эффекты при этом не наступали: наборы payload не
  пересчитывались по отредактированному шаблону (селектор Payloads продолжал
  описывать запрос в том виде, в каком его загрузили), последнее выделение не
  запоминалось — `_last_editor_selection` оставался `None`, и «mark selection»
  было нечего оборачивать в `§`; автосохранение таба тоже не запускалось.
  Гвард — `tests/unit/tui/test_intruder_template_editor_messages.py`: печать в
  шаблоне вызывает `_update_payload_select`, выделение попадает в
  `_last_editor_selection`, а `Changed`/`SelectionChanged` от чужого
  `TextArea` игнорируются.
- **Редактор не читается, пока он не собран.** Новая вкладка Repeater
  открывалась пустой по двум независимым причинам. Первая: `TabbedContent`
  объявляет свежий таб дважды, второй `TabActivated` приходит раньше, чем тело
  собрано, а `on_tabbed_content_tab_activated` первым делом зовёт
  `_save_current_tab_state()` — тот читал несуществующий редактор, получал `""`
  и записывал его в `state.request_text`. Появился `_TabState.ui_ready`: флаг
  встаёт только после удачного `load_raw`, а сохранение неготового таба —
  no-op. Вторая: панель монтируется раньше своих детей, `load_raw` глотал
  `NoMatches` от ещё не собранного `#cp-body-widget` и отчитывался об успехе —
  теперь у `ContentPanel` есть `content_mounted`, а `_init_tab_content`
  дожидается сборки через `call_after_refresh` (`_MOUNT_ATTEMPTS = 5` попыток,
  дальше — `logger.error`). Сбой восстановления текста перестал быть
  `logger.debug`: пустая восстановленная вкладка — потеря данных, а не
  диагностическая мелочь. Гвард —
  `tests/unit/tui/test_repeater_new_tab_request.py`: новая вкладка показывает
  дефолтный запрос, вторая не затирает первую, сохранение неготового таба —
  no-op.
- **Нестабильность снапшота убирается в источнике, а не нормализацией.**
  Статусбар печатает часы раз в секунду, поэтому у `PentoolApp` и `StatusBar`
  появился шов `now` (`PentoolApp(now=...)` → `StatusBar(now=...)`), а набор
  подставляет `FrozenClock` с `12:00:00`. Снимок берётся, только когда экран
  остановился: `settle()` в `tests/snapshot/helpers.py` ждёт именованный предикат
  готовности (`_repeater_ready`/`_intruder_ready` — редактор есть и в нём есть
  текст) и три подряд одинаковых `export_screenshot()`. Оба условия нужны:
  неподвижный экран ещё не значит правильный, а снимок посреди анимации — не
  кадр, который стоит закреплять.
- **Сравнение и хранение эталонов отданы библиотеке (F-032, 2026-11-16).**
  288 строк своей обвязки — запись файлов, диффы, свой флаг
  `--snapshot-update`, своя нормализация — заменил `pytest-textual-snapshot`;
  эталоны лежат в `tests/snapshot/__snapshots__/test_screens/*.raw`, обновление —
  `pytest tests/snapshot --snapshot-update`. Нормализации не осталось ни одной:
  id `terminal-N-` Rich выводит из содержимого, поэтому при неизменном экране он
  стабилен — проверено двумя прогонами сравнения подряд. Гвард —
  `tests/snapshot/test_snapshot_contract.py`: у каждого теста есть эталон и
  наоборот, эталоны не побайтовые копии друг друга, в каждом видно `12:00:00`
  (то есть время не вырезается, а часы действительно заморожены).

Правило, которое из этого следует: читать у сообщения его собственное поле и не
считать «виджет смонтирован» синонимом «виджет собран»; нестабильное значение
(часы) замораживается швом в коде, а не вырезается регуляркой из эталона.

Остаток: гонка Repeater закрыта ожиданием по фреймам, а не событием готовности
редактора, — `wait_for`/`settle` и `_wait_text` в
`test_repeater_new_tab_request.py` отсчитывают `pilot.pause()` с потолком. Из 176
строк диффа `intruder/screen.py` поведение меняют только два хендлера выше,
остальное — приведение к формату ruff.

### 11. Состояние вкладки фиксируется до смены активной

`TabbedContent` присылает `TabActivated` уже после того, как код выставил новую
активную вкладку, а обработчик первым делом сохраняет текст уходящей вкладки —
через `_active_tab_id`. Если поле к этому моменту указывает на новую вкладку, а
её редактор ещё не собран, `_save_current_tab_state()` выходит no-op по
`ui_ready`, и набранный текст остаётся только в виджете (Repeater, 2026-11-16).

Видимая потеря возникает не при переключении, а на восстановлении проекта:
вкладка открывается с прежним запросом, потому что в `state` и в историю попал
старый текст. Симптом коварный — в текущей сессии всё выглядит целым, потому что
виджет живёт в DOM.

Правило: любое действие, которое меняет `_active_tab_id` (`action_new_tab`,
`action_close_tab`, восстановление из БД), сначала фиксирует состояние текущей
вкладки. `ui_ready` защищает от записи пустоты в неотрисованную вкладку, но не
заменяет порядок вызовов — он лишь делает ошибку молчаливой.

`is_dirty` (метка `*`) к этому отношения не имеет: она считается только
относительно `last_sent_text`, и у вкладки, которую ещё не отправляли,
сравнивать не с чем, поэтому правка не помечается — это дизайн, а не потеря.

Гвард: `tests/unit/tui/test_repeater_tab_state_survives.py` — правка при
открытии новой вкладки, правка при обычном переключении, закрытие вкладки
(состояние и панель снимаются, соседняя вкладка цела, последняя не закрывается).

Открытый вопрос закрыт в тот же день (F-053): набор вкладок переехал в
отдельную таблицу `repeater_tabs` со стабильным `tab_uid`, upsert по нему и
`delete_tab` при закрытии; `repeater_entries` остаётся историей отправок и
закрытием не чистится. Вкладка теперь попадает в реестр сразу после сборки, а
не только после первой правки.

Чтобы переход не выглядел потерей, при пустом реестре и непустой истории
вкладки один раз собираются из истории по прежним правилам и записываются в
реестр (`seed_tabs_from_history`). Дальше источник истины — только реестр;
повторный вызов миграции ничего не делает.

Заодно `_close_all_tabs()` переведён на `TabbedContent.clear_panes()`: снятие
панелей по одной оставляло внутренний `Tabs` обновляющим `active` по исчезнувшей
панели (`ValueError: No Tab with id '--content-tab-tab-N'`), и это всплывало на
перезагрузке проекта, когда на экране была ровно одна вкладка.

Ещё одно следствие, важное для тестов: экран берёт путь к базе из
`AppMixin._get_db_path()`, то есть из конфигурации машины. Поэтому unit-прогон
писал в историю настоящего проекта — после него у пользователя появлялись
вкладки, которых он не создавал. `tests/unit/tui/conftest.py` уводит этот путь
в пустоту для всех TUI-тестов; тесты, которым нужна настоящая схема, задают
свой `tmp_path` и перекрывают подмену.

### 12. Экраны модулей монтируются лениво (`screen_lifecycle`)

До 2026-11-20 все 13 экранов модулей собирались в `compose()` приложения и жили
в DOM всю сессию: ~1600 виджетов. Textual на каждое действие прогоняет
idle/refresh-цикл, который даёт **≈5–6 служебных сообщений-`Callback` на каждый
смонтированный виджет**, а диспетчеризация каждого сообщения стоит ~0.13 мс
(внутри — `inspect.signature`). Замер на 120×40: клик по тоглу фильтра — **1444 мс**
при всех экранах, **321 мс** при одном активном. Отсюда «каждое действие — секунда».

Как теперь (модули `pentool/tui/screen_lifecycle.py` + `app.py`):

- `compose()` монтирует только стартовый экран; остальные создаются при первом
  переключении и **снимаются с дерева**, когда пользователь уходит.
- Политика — в `LazyScreenManager`: `plan_switch(target, mounted, keep_alive)` —
  чистая функция (что смонтировать/снять), сам менеджер применяет план через
  протокол `ScreenHost` (его реализует `PentoolApp`: `mounted_modules`,
  `get_module`, `mount_module`, `unmount_module`, `show_module`). Никакого
  Textual в планировщике — юнит-тесты гоняют его на фейковом хосте
  (`tests/unit/tui/test_screen_lifecycle.py`).
- **Три способа достать экран** (только они, `query_one(SCREEN_*)` больше нет):
  - `app.module_screen(module_id, Cls) -> Cls | None` — только если смонтирован.
    Для обработчиков, которым достаточно ничего не делать (события прокси,
    обновление надписей).
  - `app.require_module_screen(module_id, Cls)` — как `module_screen`, но кидает
    `ScreenNotMounted` (наследник `NoMatches`), поэтому старые
    `except NoMatches: log` продолжают работать без правок.
  - `await app.ensure_module_screen(module_id, Cls)` — **get-or-mount**. Для действий,
    которые обязаны сработать с любой вкладки: «Send to Repeater/Intruder/
    Scanner/Decoder/Comparer», горячие клавиши подвкладок Proxy, seed `--url`.
- **Проект переключился, а экран не смонтирован** → `mark_screen_stale()`;
  менеджер сам вызовет `ProjectManager.reload_screen(module_id, screen)` при
  следующем монтировании. Поэтому несмонтированный экран не может показать
  данные прошлого проекта, а `_reload_project_screens` больше не логирует
  «not switched» для каждого закрытого модуля.
- Новый виджет в `ContentSwitcher` монтируется скрытым (`display = False`), если
  он не текущий: `ContentSwitcher` прячет только те детей, которые знал на момент
  смены `current`, иначе новый экран нарисовался бы поверх текущего.

Подводные камни:

- `mount`/`remove` асинхронны → `_switch_to` остаётся синхронным (его зовут
  `action_*` и тесты) и запускает воркер `_activate_module`, а пока экрана нет —
  работает только «внешняя» часть переключения (`_after_module_switch`).
- Всё, что читает экран **после** переключения, должно быть async или терпеть
  `None`; синхронный `query_one` после смены модуля больше не работает.
- **Политика `keep_recent=1`** (один запасной экран): возврат туда, где были,
  мгновенный; иначе повторный mount стоит 600–1100 мс. Каждый лишний
  смонтированный экран стоит ~50–110 мс на *каждое* действие, поэтому запасной
  ровно один; менять только с замером.
- Замер после переделки (120×40): клик по тоглу фильтра 1444 → **238 мс**,
  «r» (обновить) 537 → **118 мс**, виджетов в дереве 1591 → 94–356.

**Гвард** (`tools/check_lazy_screens.py`, pre-commit-хук `check-lazy-screens` +
шаг в CI) держит три правила, каждое из которых уже ломалось в этом дереве:

1. никакого `query_one(SCREEN_X)` / `query_one("#screen-…")` /
   `query_one(SomeScreen)` для экранов модулей — только три способа выше;
2. `PentoolApp.compose()` собирает один экран (стартовый) — иначе возвращается
   обход дерева в 1600 виджетов;
3. результат `module_screen()`/`ensure_module_screen()` обязан быть проверен на `None`
   до обращения к атрибутам, и проверка должна стоять **до** использования
   (`if proxy is None: return` над `proxy.refresh()`).

Сам гвард покрыт тестами (`tests/unit/tui/test_check_lazy_screens.py`): на каждый
запрет есть фикстура с нарушением и с правильным кодом, плюс проверка, что
реальное дерево чистое.

## Инварианты и подводные камни

- **Каждый экран имеет собственный `.tcss`** рядом с `.py`; файлы попадают в
  wheel через `[tool.setuptools.package-data]` (`*.tcss`, `**/*.tcss`) — без
  этого wheel собирается, но падает в рантайме с `FileNotFoundError`.
- **PRO-экраны условны**: `ReconScreen` и `ScannerScreen` импортируются только
  при наличии сабмодуля `pro`; иначе — fallback `scanner_unavailable.py`.
- Вкладки адресуются `tab_uid`, а не именем/индексом: переименование вкладки
  не должно терять сохранённое состояние.
- **Долгая работа вкладки умирает вместе с вкладкой.** Атака Intruder — не
  исключение: воркер запускается с `group=f"intruder-attack-{tab_id}"`,
  закрытие вкладки снимает группу (`workers.cancel_group`) и отдельно просит
  встать саму атаку, `on_unmount` экрана гасит все живые. Воркер без `group=`
  нельзя снять точечно — только `cancel_all`, то есть вместе с чужими
  (F-015, ADR-11).
- **`@work` без `group=` не бывает.** Это не стилистика: `cancel_all` — не
  «снять работу экрана», а «снять всё, включая чужое». Группа называет
  назначение (`target-scope`, `target-crawl`, `dashboard-stats`), а не
  функцию. Если одно состояние правят несколько воркеров — общая группа плюс
  `exclusive`; если группу надо снять не только из декоратора (например, из
  `on_unmount`), имя выносится в константу класса. Гвард — AST-тест
  `tests/unit/tui/test_worker_groups.py`, а не список имён.
- **Работа, которая переживает экран бессмысленно, снимается в `on_unmount`.**
  Сейчас это ровно обход сайта: он идёт минутами, держит сеть и процесс-пул, а
  за пределами Target его результат некому показать. Вместе с воркером
  уменьшается счётчик активных обходов — снятый отменой воркер до своего
  `finally` может не дойти.
- **В `on_unmount` DOM уже снят.** Textual размонтирует поддерево до вызова
  `on_unmount` самого узла, поэтому `query_one` там поднимает `NoMatches`.
  Всё, что нужно погасить, держим в атрибуте экрана (`_live_attacks`), а не
  ищем в дереве; воркеры остановки запускаем на `App` — собственный
  `cancel_node` из того же `on_unmount` снял бы их раньше, чем они
  выполнятся.
- `StartStopWidget` — единственный источник логики Start/Stop.
  `set_paused(False)` возвращает «⏸ Pause» только если `_running`; иначе
  «▶ Start». Без этого `set_running(False)` + `set_paused(False)` (пара,
  которой экран синхронизирует таб) оставляла свежий таб «запущенным».
- **`AppMixin` — источник `err`/`_get_proxy`/`_get_proxy_api`/`_get_db_path`/
  `_send_to_decoder`.** Экран, вызывающий `self.err(...)` или
  `self._get_db_path()`, обязан иметь `AppMixin` в базах; гвард —
  `tests/unit/tui/test_app_mixin_surface.py`. Путь к БД — только
  `app.db_path`.
- **`ProxyService` приходит в `ProxyScreen` конструктором**, не присваиванием
  приватного поля снаружи (F-012); гвард —
  `test_proxy_service_injection.py` (AST-скан запрещает
  `<obj>._proxy_service =`).
- **AI-гейтованный контрол адресуется по id**, а не классом на весь экран, и
  видимость переприменяется при монтировании вкладки (F-022); гвард —
  `test_intruder_ai_visibility.py`.
- **Один циклер — `OptionCycler`**; в фильтр-барах он создаётся с
  `allow_empty=True` (опция 0 = «Any») и `suffix=" ▼"`.
- **Фильтры истории — `HistoryFilterBar`** (`ProxyFilterBar`, `WsFilterBar`):
  общая композиция, тоглы Scope/Comments, один `.tcss` с селекторами по
  базовому классу.
- **`on_resize` меняет класс, а не состояние пользователя** (F-027/ADR-7).
  `PentoolApp.on_resize` ставит `narrow` на активный `Screen` при ширине
  `< NARROW_BREAKPOINT` (80); что спрятать — решает CSS в `app.tcss`. Старый
  код звал `ProxyScreen.action_toggle_inspector()`, то есть переключал
  `_inspector_visible`: терминал сужался — инспектор исчезал навсегда, потому
  что обратно флаг никто не ставил. Гварды —
  `tests/unit/tui/test_responsive_layout.py`: реальный прогон с
  `resize_terminal` туда-обратно плюс AST-скан `on_resize` на запрет вызовов
  `action_toggle_inspector`/`action_hide_detail`.
