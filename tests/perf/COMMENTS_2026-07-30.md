# Комментарии к отчёту Perf/Memory Quick Check (2026-07-30)

Ниже — интерпретация цифр из `REPORT_2026-07-30.md`. Смотрел только на результаты
замеров (время, RSS, tracemalloc-diff), в реализацию модулей не заходил.

## 🔴 Узкое место №1 — Scanner: не уложился даже в 90 секунд

**Факт**: скан 60 URL × 23 активных чека не завершился ни за 150с (без лимита),
ни за 90с (с жёстким `wait_for`). Пришлось искусственно обрубать, иначе
процесс завис бы неопределённо.

**Почему это важно**: это не гипотетическая "утечка при часах работы" — это
рабочий сценарий обычного использования (пользователь сканирует сайт из
десятков страниц). Если 60 URL не укладываются в 1.5 минуты — на реальных
целях с сотнями эндпоинтов время скана станет неприемлемым для интерактивного
TUI-инструмента.

**Вероятные причины (по косвенным признакам из лога)**:
- Комбинаторный взрыв: 23 чека × N инъекционных точек (headers, query, body)
  × payloads на чек — задача явно multiplies quickly, судя по количеству
  повторяющихся строк лога на **одну и ту же точку** (`Referer`, `User-Agent`,
  `X-Forwarded-For`, ...) для каждого чека отдельно.
- Time-based чеки (SQLi blind, SSTI) обычно ждут искусственные задержки
  (`sleep(5)` и т.п.) для детекции — на 23 чеках × много точек это легко
  даёт сотни секунд суммарного ожидания, даже при конкурентности.
- Мок-сервер не является уязвимой целью — но это не должно приводить к
  тайм-аутам такой длины, если чеки корректно фейлят быстро на "чистом" ответе.

**Рекомендации**:
1. Профилировать сценарий scanner отдельно через `py-spy record` или
   `memray run` — обязательно, чтобы увидеть, где реально тратится время:
   в HTTP-ожиданиях, в самих чеках (парсинг/regex) или в конкуренции
   (semaphore слишком узкий).
2. Проверить фактическое значение `concurrency` в `ScanEngine` (дефолт=5
   в конструкторе, судя по сигнатуре) — возможно, для 60 URL × много тасков
   это создаёт очередь, где полезно поднять конкурентность или сделать её
   адаптивной.
3. Ввести **软 таймаут на чек/точку** (не только на весь скан) — если один
   time-based чек виснет на blind-detection, это не должно тормозить всю
   очередь остальных чеков.
4. Добавить в TUI индикатор ETA/прогресса, если время скана останется
   высоким — сейчас пользователь не может отличить "долго, но идёт" от
   "зависло".

## 🟡 Узкое место №2 — DataTable/ArrowBackend: +179 MB на 50k строк

**Факт**: самая большая единичная просадка памяти во всём прогоне — рост RSS
на 179 MB при вставке 50 000 строк в ArrowBackend.

**Важный нюанс**: судя по tracemalloc-diff, **основной вклад — это разовый
импорт pyarrow/pandas** (`importlib._bootstrap_external` +20 MB,
`pandas/util/_decorators` +331 KB), а не сами данные таблицы. Это означает,
что часть роста — единоразовая стоимость первого обращения к pyarrow в
процессе, а не стоимость на каждые 50k строк.

**Рекомендации**:
1. Перепрогнать сценарий **дважды подряд в одном процессе** (вторая вставка
   после того, как pyarrow уже импортирован) — это отделит "стоимость
   импорта библиотеки" от "стоимости самих данных". Сейчас в отчёте это
   не разделено, и вывод "179 MB за 50k строк" может вводить в заблуждение.
2. Если реальный рост на сами данные тоже существенный — проверить, что при
   пересборке `ArrowBackend` (когда Proxy делает
   `table.backend = ArrowBackend(arrow)` при каждом батче, как видно из
   `screen.py`) старые pyarrow-таблицы действительно освобождаются, а не
   висят до сборки мусора. Учитывая, что Proxy может накапливать десятки
   тысяч строк за сессию — это прямая точка риска на длинных сессиях.
3. Замерить память при **10k/50k/100k** строк одним прогоном, чтобы понять,
   рост линейный или там есть скачки (например, из-за реаллокаций Arrow
   буфера).

## 🟢 Proxy/HttpStorage — в пределах нормы, но неполно протестировано

**Факт**: 5000 запросов → +8.2 MB RSS, 3.94 MB БД. Выглядит здорово, но:

**Ограничение теста**: тела ответов в сценарии были фиксированные "x"×500 —
то есть маленькие. `HttpStorage` имеет отдельную логику `_LARGE_BODY_THRESHOLD
= 1 MB` (large_body_handler) — **этот сценарий её вообще не затронул**.

**Рекомендация**: обязательно отдельный прогон с телами >1MB (например,
10% запросов с 2-5 MB телом), чтобы проверить путь `large_body_handler` —
именно там больше шансов на утечку/раздувание памяти, т.к. это специальный
код для "тяжёлых" тел.

## 🟢 Intruder — в пределах нормы

**Факт**: 400 запросов (cluster bomb 20×20) → +7.4 MB, 4.48с. Спокойно.

**Ограничение теста**: тестировался только "Standard mode". В коде виден
отдельный `TurboIntruderAttack` (`turbo_mode=True`, connection pooling +
Keep-Alive) — именно он предназначен для больших словарей/throughput, и
именно там выше риск по памяти (пул соединений, буферизация). Он не был
протестирован.

**Рекомендация**: повторить сценарий с `turbo_mode=True` и большим словарём
(2000-5000 payloads) — это тот путь, который реально используется при
серьёзных атаках, и текущий тест его не покрывает.

## 🟢 Dashboard/LiveChart — не проблема

10 000 push-событий — 0.0 MB роста, 0.1с. Это ожидаемо: `deque(maxlen=60)`
ограничивает историю константным размером независимо от числа событий.
Единственный неограниченно растущий счётчик — `self._total` (просто int),
угрозы для памяти не несёт. Здесь можно не тратить время на дальнейшее
тестирование.

## Общие ограничения проведённого тестирования (что НЕ проверено)

1. **TUI-слой не тестировался вообще** — все сценарии дергают API/модули
   напрямую, без реального Textual App. Реальный рендеринг, message queue
   Textual, обработчики событий — отдельная зона риска, которую 15-минутный
   прогон не покрывает.
2. **Одновременная многомодульная нагрузка** — например, Proxy пишет трафик
   ПОКА Scanner сканирует ПОКА Intruder атакует. Именно так выглядит реальная
   сессия пользователя, а тестировалось всё изолированно по одному.
3. **Long-running / утечки во времени** — как и договаривались, это разовые
   плотные прогоны, не многочасовые. Если утечка проявляется медленно (растёт
   на 1 MB за час), эти тесты её не поймают в принципе.
4. **CPU-профиль не снят** — договаривались использовать py-spy, но в рамках
   быстрого 15-минутного прогона сделан только RSS+tracemalloc (это отвечает
   на "сколько памяти", но не на "где горячий CPU-путь"). Учитывая находку
   по Scanner (96 секунд на 60 URL) — это первая цель для py-spy profiling.

## Приоритет следующих шагов (если продолжать)

1. **Scanner performance** — py-spy профиль скана, разобраться в 96-секундной
   задержке. Это единственная находка уровня "блокер", а не "оптимизация".
2. Повторный тест DataTable без единоразовой стоимости импорта pyarrow —
   уточнить реальную стоимость на 50k/100k строк.
3. Proxy storage с большими телами (>1MB) — покрыть `large_body_handler`.
4. Intruder в Turbo Mode с большим словарём.
