## Что реально изменилось (подтверждено измерениями)

### 🟢 Память — Proxy live-append теперь без всплеска RSS
Раньше каждая пачка живого трафика (100 запросов, debounce 150ms) давала
**+0.4 MB** за счёт полной пересборки `ArrowBackend` (`table.backend =
ArrowBackend(new_table)` создаёт новый `pa.Table` целиком). После перехода
на `table.add_rows()` — **+0.0 MB**, потому что `append_rows()` дописывает
только новые строки Arrow-батчем, без пересоздания всей структуры. При
долгой сессии с постоянным трафиком это должно давать заметно более
плоский профиль памяти (раньше каждая debounce-пачка = ещё один
промежуточный `pa.Table`, который ждёт GC).

### 🟢 Proxy/HttpStorage — небольшое снижение RSS (-20%)
+6.6 MB против +8.2 MB на 5000 запросов. Скорее всего эффект от снижения
`_pre_storage_queue`/структур не при чем напрямую — реального объяснения в
рамках этого теста нет (сценарий не трогает EventBus/ProxyServer.requests
вообще, только HttpStorage). Разница в пределах типичного шума между
прогонами (~1-2 MB), не считаю значимым результатом без повторных
замеров.

### 🎯 Не про память/CPU, но главный практический результат — прозрачность
Раньше пользователь **тихо** терял видимость 6000 из 8000 запросов при
Reload/открытии проекта — лимит 2000 срабатывал без индикации. Теперь:
- Лимит явно снижен до 1000 (осознанно, обсуждали) — экономит RSS на
  холодном старте большой истории (1000 строк вместо 2000 в памяти сразу).
- Пользователь **видит** "Showing 1000 of 8000 — scroll up to load more" —
  пропавшие данные больше не пропадают молча.
- Подгрузка по скроллу вверх работает (не проверено live-тестом Pilot в
  этом раунде — нет теста на сам скролл-триггер, только на факт первичной
  загрузки; стоит закрыть отдельным тестом).

### 🟡 EventBus/ProxyServer._requests_max — не проявилось в текущих тестах
Пункты 2 и 3 (EventBus.for_history() убирает полный `InterceptedRequest`
из `_history`, `clear_history` теперь чистит и EventBus) **не покрыты
существующими perf-сценариями** — ни `quick_check.py`, ни `tui_deep.py` не
эмулируют объём трафика, достаточный чтобы EventBus._history (maxlen=10000)
реально заполнился и держал много полных объектов. Эффект от этих правок
teoretически должен быть заметен при **долгой сессии с тысячами запросов**
через реальный Proxy (не через `HttpStorage.add_request()` напрямую, как
делает текущий сценарий `scenario_proxy_storage`), либо при явном вызове
`action_clear_list()` после накопления истории в EventBus.

**Рекомендация**: если хотите количественно подтвердить пункты 2/3 —
нужен отдельный сценарий: эмулировать N `ProxyRequestCaptured`/
`ProxyRequestCompleted` событий через `EventBus.emit()` напрямую (не через
HttpStorage), замерить RSS до/после, затем вызвать `clear_history()` и
убедиться что RSS падает. Текущие тесты этого не делают.

## Итоговый вывод

1. **Единственный количественно подтверждённый выигрыш** в этом раунде —
   Proxy live-append теперь не даёт всплеска RSS при живом трафике
   (+0.4 MB → +0.0 MB на пачку). Это **напрямую снимает узкое место**,
   которое ранее churn-тест DataTable уже показывал как "не проблема в
   среднем", но конкретно debounce-путь Proxy всё же расходовал лишнюю
   память на каждую пересборку.
2. **Не количественно подтверждено** (нет подходящего теста): экономия от
   EventBus.for_history() и снижения `_requests_max` 10000→1000 —
   ожидаемо значимая при долгой сессии/большом трафике, но текущие
   быстрые 15-минутные сценарии её не нагружают настолько, чтобы увидеть
   разницу.
3. **Не изменилось (и не должно было)**: Scanner (96с — отдельная,
   непочиненная в этом раунде проблема), DataTable разовая вставка
   50k строк, Intruder, Dashboard, время запуска/навигации TUI — все эти
   пути не были целью текущих правок.
4. **Главный практический эффект** — не про "быстрее/меньше памяти", а про
   **корректность UX**: тихая потеря видимости 6000/8000 запросов
   заменена на явный, честный счётчик.

## Что осталось непроверенным / следующие шаги
- Нагрузочный тест EventBus.emit() на объёме, где разница до/после
  `for_history()` реально видна (тысячи `ProxyRequestCaptured` с телами).
- Отдельный тест на сам scroll-to-top триггер подгрузки истории (сейчас
  проверена только начальная загрузка первой страницы).
- Scanner (96 секунд на 60 URL) — по-прежнему главный блокер, не входил в
  объём этой сессии правок.
